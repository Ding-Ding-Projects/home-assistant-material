### Top-level page frame is 100vh tall, so on phone browsers its end sits below the visible screen

`frontend/src/components/ha-top-app-bar-fixed.ts:36`, scroll, confidence medium, board reference `design/canvases/42-modern-polish-2/README.md (rule 3: the end of a page clears every fixed or floating thing)`

**What happens.** The :host of `ha-top-app-bar-fixed` (lines 33-43) is `height: 100vh; overflow: hidden`, and the only scroller, `.top-app-bar-fixed-adjust` (278-290), is absolutely positioned with `bottom: 0` inside it. On mobile Chrome and Safari, 100vh is the large viewport (browser bar hidden), so while the address bar is showing the host and its scroller extend 56-80 px below the visible bottom edge. The scroller's `padding-bottom` (293-299) only reserves the `bottom-bar` safe area, so the last content ends under the phone bar. `hass-subpage` and `hass-tabs-subpage` size themselves with `position: fixed; height: 100%` on phones, which follows the dynamic viewport, and `hass-tabs-subpage-data-table` already uses `height: 100vh; height: 100dvh` (lines 2072-2073). Only this frame keeps a bare 100vh. It is used by History, Logbook, Map, Climate, Light, Security, Maintenance, Media browser, Not found, the error and loading screens, and the dashboard YAML editor.

**At phone and desktop width.** 390 px phone in a browser (not the companion app): scrolled to the end, the last 56-80 px of History, Logbook or Media content stay behind the floating bottom bar until a document scroll collapses the address bar. Desktop: no visible effect, because 100vh equals the window height there.

**Fix.** Line 36 of haTopAppBarFixedStyles: keep `height: 100vh;` and add `height: 100dvh;` after it. Also in `ha-panel-history.ts:1111`, add `height: 100dvh;` after `height: 100vh;`, or drop the height declaration there so the component rule applies.

**Second reviewer.** Confirmed. The :host rule at `ha-top-app-bar-fixed.ts:36` is `height: 100vh; overflow: hidden`. The scroller at 278-290 is absolute with `bottom:0`, and the narrow padding at 293-299 is only `safe-area` plus `dim-sum` reserve. html itself is 100vh (`main.globals.ts:6`), so in a mobile browser the document is only scrollable by the `address-bar` height. The phone bar is fixed to the visible bottom and `--ha-phone-viewport-inset-bottom` (innerHeight - `visualViewport.height`) stays about 0 while the bar shows, so nothing makes up the gap. The fix is incomplete: `ha-panel-history.ts:1110-1114` styles the host from outside with `ha-top-app-bar-fixed { height: 100vh; ... }`. An `outer-scope` rule beats :host, so History keeps 100vh even after the component fix.

### Empty state of every list page is centred in a non-scrolling box that runs under the bottom bar and the Create button

`frontend/src/layouts/hass-tabs-subpage-data-table.ts:2579`, clip, confidence high, board reference `design/canvases/42-modern-polish-2/README.md (rules 1 and 3)`

**What happens.** The `data-table` layout always runs `hass-tabs-subpage` in `inner-scroll` mode (line 1120), which makes .content `overflow: hidden` (`hass-tabs-subpage.ts` 1148-1152) and turns off the narrow `padding-bottom` (1156-1161 only match `:not([inner-scroll`])). When the list is empty, .center (2222-2225 and 2579-2588) holds the `slot="empty"` content: `flex: 1 1 auto; min-height: 0; height: 100%; display: flex; align-items: center; justify-content: center; padding: 16px`. It has no overflow and no bottom inset. The table itself reserves `safe-area + endSpace` at its end (line 1248), but the empty state gets none of that. Unsafe centring also pushes overflow out of both the top and the bottom.

**At phone and desktop width.** 390 x 667 px phone with no automations: the empty block from `ha-automation-picker.ts:1002-1030` (80 px icon, heading, two paragraphs and a Learn more link) is centred in a box whose lower 76 px sit under the phone bar. The fixed Create automation button (bottom 16 px + safe area) lands over the lower part of the block, and nothing scrolls it clear. In bilingual mode or at larger text sizes, the top of the icon and heading is cut off with no way to reach it. Desktop: in a short window (for example 600 px tall at 125 % zoom) the same block is clipped at the top and bottom with no scrollbar.

**Fix.** On .center (line 2579) add `overflow-y: auto; align-items: safe center; justify-content: safe center;`. Pad its end clear of the floating controls the way the table is: in render (line 1203), set `style=${styleMap({"padding-bottom": ``calc(16px` + `var(--safe-area-inset-bottom`, 0px) + ${endSpace}px)`})}` on the .center div.

**Second reviewer.** Confirmed. `hass-tabs-subpage-data-table` always renders `hass-tabs-subpage` with `inner-scroll` (line 1120). `:host([inner-scroll`]) .content is `overflow: hidden`, and the narrow `padding-bottom` rule only matches `:not([inner-scroll`]) (`hass-tabs-subpage.ts:1148-1161`). The data table does not pass hasFab, so no `fab-bottom-space` is rendered. On a phone, `:host([narrow`]) is `position:fixed` `height:100%`, so .content runs to the bottom of the screen under the bar. .center (2222-2225 and 2579-2588) is `height:100%`, centred with plain center, has no overflow and no bottom inset. Only the table branch gets the endSpace spacer (line 1248). The automation picker's .empty block (80 px icon, h2, two paragraphs, a button) is a realistic overflow case. The proposed fix is sound: .center already has `min-height:0`, and endSpace covers the FAB height.

### List pages and top-level pages do not reserve room for the phone toast strip, so a toast covers the last row

`frontend/src/layouts/hass-tabs-subpage-data-table.ts:1248`, scroll, confidence high, board reference `design/canvases/42-modern-polish-2/README.md (rule 3)`

**What happens.** `notification-manager.ts:125-135` publishes `--ha-toast-reserved-height` while toasts show in the phone strip above the bottom bar. `hass-subpage` (550-562) and `hass-tabs-subpage` (1156-1171) add it to their end padding. The `data-table` layout sizes the list's end spacer as `calc(var(--safe-area-inset-bottom, 0px) + ${endSpace}px)` (line 1248, used by `ha-data-table.ts:2335-2339` `.empty-row`) without the toast height. In `inner-scroll` mode the subpage padding that would include it is switched off. `ha-top-app-bar-fixed.ts:293-299` also pads by safe area plus `--ha-dim-sum-reserved-height` only, with no toast term.

**At phone and desktop width.** 390 px phone: after an action that shows a toast (for example Undo after deleting, or a reconnect notice), the last device, entity or automation row sits under the toast. Scrolling to the end does not bring it clear while the toast is up. The same applies to the end of History, Logbook and Media pages. Desktop: no effect, because the toast strip is only reserved on narrow viewports.

**Fix.** Line 1248: change the value to `calc(var(--safe-area-inset-bottom, 0px) + var(--ha-toast-reserved-height, 0px) + ${endSpace}px)`. In `ha-top-app-bar-fixed.ts:295-298`, add `+ var(--ha-toast-reserved-height, 0px)` to the narrow `padding-bottom` calc.

**Second reviewer.** Confirmed. `notification-manager` sets `--ha-toast-reserved-height` on <html> while phone toasts show. `hass-subpage` (553, 560) and `hass-tabs-subpage` `non-inner-scroll` (1159, 1170) add it, but the `data-table` end spacer at line 1248 and the narrow padding at `ha-top-app-bar-fixed.ts:295-298` do not. One nuance on list pages: endSpace = 16 + `max(dock`, fab) + 16 above the bar. The toast stack sits at `safe-area` + 16 + phone bar, the same baseline as the FAB and dock, so a single `one-line` toast mostly falls inside the band already reserved. The `data-table` half bites for `multi-line` or stacked toasts. The `ha-top-app-bar-fixed` half (History, Logbook, Media, which have no FAB or dock reserve) is the clear case. The proposed fix matches what the other layouts already do.

### Layouts force display:flex on ha-menu-button, defeating the phone hide rule and leaving an empty tonal circle when the button has nothing to show

`frontend/src/layouts/hass-subpage.ts:467`, modernize, confidence medium

**What happens.** `home-assistant-main.ts:494` sets `--ha-phone-menu-button-display`: none, and `ha-menu-button.ts:142-144` reads it in `:host { display: var(--ha-phone-menu-button-display, inline) }`, because the bottom bar already has Menu. `hass-subpage.ts:464-471` and `hass-tabs-subpage.ts:1084-1091` style the host from outside with `display: flex`. `Outer-scope` rules beat :host rules, so the variable never applies. Separately, `page-entry.ts:166-184` gives the host a 48 px size, 50 % radius and a `secondary-container` background. When `ha-menu-button` renders `nothing` (`ha-menu-button.ts:68-71`: desktop with a docked or auto sidebar, or kiosk mode), the styled empty host is still drawn. `hass-tabs-subpage.ts:828-832` also adds a 24 px `inline-end` margin to it. `ha-config-dashboard.ts:381-388` shows the intended pattern: it only renders the button when narrow.

**At phone and desktop width.** 390 px phone: Profile (`hass-subpage` `main-page`) and pages opened as the first history entry show a second Menu button in the page header next to the `bottom-bar` Menu. On `hass-tabs-subpage` pages it carries an extra 24 px gap that takes room from the title. Desktop: the same main pages show a 48 px filled circle before the title that does nothing when clicked, because the click handler is on the inner `ha-icon-button` that was not rendered.

**Fix.** Remove `ha-menu-button` from the `display: flex` selector lists at `hass-subpage.ts:464` and `hass-tabs-subpage.ts:1084`, and add `ha-menu-button { display: var(--ha-phone-menu-button-display, flex); }`. In `ha-menu-button.ts` willUpdate, call `this.toggleAttribute("hidden", !this._show)` and add `:host([hidden]) { display: none !important; }` so an empty host never paints. Delete the 24 px margin rule at `hass-tabs-subpage.ts:828-832`; the toolbar gap already spaces it.

**Second reviewer.** Confirmed. `ha-menu-button's` :host sets `display: var(--ha-phone-menu-button-display, inline)`, and `home-assistant-main` sets that variable to none on phones. `hass-subpage.ts:464-471` and `hass-tabs-subpage.ts:1084-1091` set `display: flex` on the element from the outer scope, and that outranks the :host rule. So on a phone the `main-page` Menu button (for example Profile, `hass-subpage` `main-page`) is shown again. On desktop, with dockedSidebar auto or docked, _show is false and render() returns nothing. pageHeaderStyles (`page-entry.ts:166-184`) still gives the host 48x48, a 50% radius and a `secondary-container` background. As a flex item it is blockified, so an empty circle paints. The 24 px margin rule at `hass-tabs-subpage.ts:828-832` exists. Note that `ha-top-app-bar-fixed` also renders a bare `ha-menu-button` in a flex .section, so History, Logbook and similar pages show the same empty desktop circle. The `ha-menu-button.ts` `hidden-attribute` part of the fix covers those as well. The `!important` is required because the outer `display:flex` would otherwise beat `:host([hidden`]).

The panel is an 88 px tile with 12 px margin, a title, the message, 24 px padding, and buttons below. In `hass-not-found-screen.ts`, use `align-items: safe center` at line 68 and `min-height: 100%` at line 65. That screen is not in a scroller, so safe centring is what keeps the top visible there.

**Second reviewer.** Real for `hass-error-screen`. ### Floating-pane gap is reported as a physical right inset while the frame uses logical insets, so in RTL the page runs under the frame

`frontend/src/layouts/home-assistant-main.ts:481`, clip, confidence medium

**What happens.** For the floating pane, `home-assistant-main` adds the 12 px pane gap to `--safe-area-inset-right` (481-484). The frame that paints the window colour around the pane is placed logically: `inset-inline-start: var(--ha-sidebar-width); inset-inline-end: var(--ha-pane-gap)` with `box-shadow: 0 0 0 100vmax` (571-583). Pages consume the physical value: `hass-subpage` .content `margin-right` and width (531-536), `hass-tabs-subpage` .content `padding-right` (1141), and `ha-top-app-bar-fixed` scroller `padding-right` (288). In a `right-to-left` language the gap is on the left, but pages still pad the right.

**At phone and desktop width.** Phone: no effect, because the pane frame is only drawn when the sidebar is not modal (wider than 870 px). Desktop in Hebrew, Arabic or Persian: the left 12 px of every page (the inline end: tool pills, row actions, and the thin vertical scrollbar, which Chrome places on the left in RTL) are painted over by the frame's `window-colour` ring. A useless 12 px empty strip appears on the right beside the rail.

**Fix.** Leave the inset variables alone. Convert the physical consumers to logical ones: `ha-top-app-bar-fixed.ts:132` and 288 `padding-right` to `padding-inline-end`; `hass-tabs-subpage.ts:841` and 1141 `padding-right` to `padding-inline-end`; `hass-subpage.ts:442` `padding-right` to `padding-inline-end`; `hass-subpage.ts:536` `margin-right` to `margin-inline-end` (keep the width calc). The pane gap then lands on the inline end in both directions, consistent with the header row and FAB rules. Caveat: on a `non-modal` landscape phone in RTL, a physical device notch inset would also move to the inline end.

**Second reviewer.** The problem is real. In RTL the drawer puts the rail on the right (`padding-inline-start`), and the pane frame's `inset-inline-end` gap ends up on the left. The scrollers use physical consumers: `ha-top-app-bar-fixed.ts:288` `padding-right`, `hass-tabs-subpage.ts:1141` `padding-right`, and `hass-subpage.ts:531-536` width calc plus `margin-right`. With `margin-right`, the RTL box spans [0, `W-12`], so content sits under the frame's left ring. The proposed fix is wrong. Several consumers already read `--safe-area-inset-right` logically and are correct in RTL today: the header row `padding-inline-end` (`ha-top-app-bar-fixed.ts` 78-80 and 88), the FAB `inset-inline-end` (`hass-subpage.ts` 578 and 617, `hass-tabs-subpage.ts` 1177) and the `data-table` pill dock (2263). Swapping the variables would strip the 12 px gap from those and push the header pill and FABs against or under the left frame edge.

### Page lock banner floats over the first rows of top-level pages instead of pushing them down

`frontend/src/components/ha-top-app-bar-fixed.ts:319`, clip, confidence medium

**Fix.** Make the banner part of the measured header: change the rule at 319-324 to `ha-page-lock-banner { position: static; }` so it lays out inside `.top-app-bar` and the existing ResizeObserver on the bar includes its height in `--total-top-app-bar-height`.

**Second reviewer.** Confirmed. `ha-page-lock-banner` is rendered inside `<header class="top-app-bar">` with `position:absolute; top:100%; z-index:1` (319-324). _updateHeaderHeight measures `.top-app-bar` offsetHeight (the @query at 350), which does not include an absolutely positioned child. So `--total-top-app-bar-height` excludes the banner and `.top-app-bar-fixed-adjust` starts under it. `hass-subpage` (271) and `hass-tabs-subpage` put the banner in normal flow. ### Voice satellite setup forces each step to 100vh, so the step buttons sit below the sheet's visible area

`frontend/src/dialogs/voice-assistant-setup/voice-assistant-setup-dialog.ts:379`, scroll, confidence high

**What happens.** At `max-width` 450px (or `max-height` 500px) `.content` gets `height: calc(100vh - 56px)` (lines 377-381), a leftover from the old `full-screen` dialog. `ha-dialog` is now a bottom sheet on phones, capped at `max-height: 88dvh` (`components/ha-dialog.ts:636-641`) with a 24px handle and a header of about 72px above the body. Every step uses `AssistantSetupStyles` (`voice-assistant-setup/styles.ts:7-15` and 24-28): `:host { min-height: 100%; justify-content: space-between }`, so the step stretches to the full 788px and its `.footer` (Next, Skip, Done) sits at the very bottom. The dialog has no footer slot: the step's own buttons are the only way forward.

**At phone and desktop width.** At 390x844 the body has about 646px (less in Safari, where 100vh is the large viewport and 88dvh the small one), while the step is 788px or more tall. The Next and Skip buttons on every step land about 140-230px below the visible sheet, and the `space-between` layout leaves a large empty gap above them, so nothing shows that more is below. The person has to scroll the sheet on every step to continue. At desktop width (over 450px wide and over 500px tall) the rule does not apply and the steps look normal.
